## 1. A prompt in a system is code

When you chat with a model, a prompt is a message. You read the reply, and if it is off, you
ask again. When a model is a step in a system, the prompt behaves differently:

- It runs **thousands of times, unattended**, on inputs you have never seen.
- Its reply is read by **code**, not by a person who can shrug off an extra sentence.
- A change to it changes the behaviour of the whole system, just as a change to a function does.

Think of the difference between briefing a colleague in person and writing a standard operating
procedure (SOP) for a field office. The briefing can be loose, because the colleague asks
questions. The SOP must work for someone you have never met, on a bad day, with a situation you
did not anticipate. It is versioned, reviewed and tested before it is issued. A production
prompt is an SOP.

This class has two halves. Sections 2–4 are about writing the prompt well. Sections 5–7 are
about everything around it that makes the output *trustworthy*: a schema, validation, a retry
loop, versioning and tests. In practice the second half matters more. A good prompt makes
failures rarer. The harness makes them harmless.

## 2. The anatomy of a prompt for systems

### Messages and roles

Chat APIs take a list of **messages**, each with a **role**:

| Role | Who writes it | What goes in it |
|---|---|---|
| `system` | You, the developer | Stable instructions: the job, the rules, the output format, examples. The same on every call. |
| `user` | The input for this call | The data to process (the field report), plus any per-call instruction. |
| `assistant` | The model | Its replies. You also write assistant messages yourself to show examples or to replay a conversation, as the retry loop does. |

--8<-- "shared/sidebars/system-prompt.md"

The split matters for engineering reasons:

- **Stable vs variable.** The system prompt is the part you version and test. The user message
  changes every call. Keeping them apart makes both easier to reason about, and many providers
  can **cache** a long, stable prefix to cut cost and latency (Class 4).
- **Instructions vs data.** Models give system instructions more weight than text in the user
  message. The field report is *data*: if it contains "ignore previous instructions", that
  should stay data. The system/user split plus delimiters is your first defence against
  **prompt injection**, instructions smuggled in through data. It is not a complete defence
  (Class 8), but without it you have none.

### The building blocks

The [AI Literacy prompting class](../literacy/c3.md) teaches six building blocks: role, task,
context, format, examples and constraints. They carry over, with an engineer's emphasis:

| Block | In a system prompt | SitRep extractor |
|---|---|---|
| **Role and task** | One or two sentences: what this step does, for whom | "You extract structured data from humanitarian field reports for a SitRep." |
| **Context** | What the model cannot guess: domain conventions, the audience, why the rules exist | Households, people and families are different units. |
| **Rules** | Numbered, specific, testable. Say what to do in the edge case, not just the normal case | "If the report does not state something, write "not stated". Never use null." |
| **Output format** | The exact schema, and "no prose, no markdown" | The JSON Schema, included verbatim |
| **Examples** | One to three worked input → output pairs | A short landslide report and its JSON |

Three habits separate system prompts that work from ones that nearly work:

1. **Specify the edge cases.** The happy path almost always works. The prompt earns its keep on
   the missing date, the ambiguous "04/05", and the figure given in families instead of
   households. Every rule you write should come from a failure you saw or can foresee.
2. **Give the reason.** "Copy figures exactly as written, because downstream code compares
   them to the source" works better than "copy figures exactly". The reason lets the model
   generalise to cases your rule didn't mention.
3. **Say it once, clearly.** Contradictory or repeated instructions ("be concise" at the top,
   "be thorough" at the bottom) make behaviour unpredictable. Capitals and threats ("YOU MUST")
   do not help modern models, and they can cause over-correction.

### Delimiters

Mark exactly where data begins and ends. XML-style tags are the most common convention, because
they are unambiguous and models are trained on a lot of them:

```text
Extract the SitRep data from this report.

<report>
heavy rain since the weekend, Tula river burst near Kessa bridge. we got to Aramu
town + Lomi and Tavet villages today. could NOT reach Dorra...
</report>
```

Triple quotes, `---` lines or Markdown headings also work. What matters is that you use one
convention consistently and that the rules refer to it ("Use only information inside
`<report>`"). With several inputs, give each its own tag: `<report id="2">`, `<previous_sitrep>`.

Here is the lab's system prompt, abridged. Notice that it contains no field report: that goes in
the user message.

```text
You extract structured data from humanitarian field reports for a situation report
(SitRep). You are careful and literal.

Rules:
1. Use only information in the report. Never estimate, infer or add figures.
2. If the report does not state something, write "not stated". Never use null.
3. Copy every figure exactly as written ("approx 1,200", "~600"). Never convert units:
   households, people and families are different units.
4. For each figure, "source" quotes the words in the report it comes from.
5. report_date is YYYY-MM-DD only if the report gives an unambiguous date; otherwise
   "not stated".
6. severity is your assessment from the report's content: one of low, medium, high,
   critical, or "not stated" if there is too little information.
7. Reply with one JSON object that matches the schema below. No prose, no markdown.

JSON schema:
{ ...the full schema... }

Example report:
<report>
landslide in Kopa hills sat night, 2026-02-07. 35 families lost houses, ...
</report>

Example output:
{ "district": "Kopa", "report_date": "2026-02-07", ... }
```

## 3. Few-shot examples

A **few-shot** prompt includes worked examples of input and output. For a system, examples are
the most efficient way to communicate a format and a level of literalness that is hard to
describe in rules.

--8<-- "shared/sidebars/few-shot.md"

Engineering guidance:

- **Examples beat descriptions for format, and rules beat examples for edge cases.** An example
  shows what a clean `affected` list looks like. A rule says what to do when there is no date.
  Use both.
- **Vary the content, keep the pattern.** The lab's example is a *landslide* in *Kopa*, while
  real inputs are mostly floods in Northern Veloria. If the example were a flood in Aramu, the
  model would be tempted to copy its places and figures. **Example leakage**, the model copying
  content from an example into a real answer, is a real failure mode. Check for it in tests.
- **Show the edge case in an example.** The lab's example output includes `"response": ["not
  stated"]` and a `gaps` list. Seeing "not stated" used once makes the model far more willing
  to use it.
- **Examples are fixtures.** Store them with the prompt, version them together, and make sure
  every example output passes your own validator. An invalid example teaches invalid output.
- **Mind the cost.** Examples are sent on every call. Three long examples can cost more than the
  report being processed. Keep them short, or rely on caching.

Examples can also be written as alternating `user` and `assistant` messages (a fake
conversation) instead of text in the system prompt. Both work. The message form makes the
example's output look exactly like a real reply, which helps with strict formats.

## 4. Reasoning in prompts

For multi-step tasks, models do better when they reason before answering. This is
**chain-of-thought** prompting.

--8<-- "shared/sidebars/chain-of-thought.md"

In a system, reasoning collides with structured output: you want reasoning *and* a clean object
your code can parse. Three patterns, as of 2026:

| Pattern | How | When |
|---|---|---|
| **Reasoning model** | Use a model that reasons internally before replying; set its reasoning effort; ask only for the final JSON | Steps that need judgement across several facts (reconciling figures, planning). Don't also ask it to "think step by step". It already does, and the extra text can conflict |
| **Reasoning field first** | Put a `"reasoning"` string as the *first* field of the schema, before the answer fields | Standard models on moderately hard steps. The model generates tokens in order, so the reasoning is written before the answer and can shape it |
| **Two calls** | One call reasons in free text; a second call (or code) extracts the structured answer | When reasoning is long, or you want to log and review it separately |

Two cautions. First, **do not parse reasoning.** It is for the model, and sometimes for a human
reviewer. Your code reads only the answer fields. Second, **reasoning is not verification.** A
fluent explanation can accompany a wrong figure. For the SitRep extractor, which copies facts
rather than reconciling them, you do not need reasoning at all. It belongs in Class 6's Analyst.

## 5. Structured outputs

Class 1's decomposition put a **code check** after every AI step. Code can only check what it
can parse. **Structured output** means the model replies in a fixed, machine-readable shape,
almost always JSON, that matches a schema you define.

--8<-- "shared/sidebars/structured-output.md"

### JSON Schema: the contract

**JSON Schema** is a standard way to describe the shape of JSON data: which fields exist, their
types, which are required, and which values are allowed. It is the contract between the model
and your code, and every provider's structured-output mode accepts it. The lab's schema,
abridged:

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["district", "report_date", "hazard", "severity", "affected",
               "priority_needs", "response", "gaps"],
  "properties": {
    "district":    {"type": "string"},
    "report_date": {"type": "string", "description": "YYYY-MM-DD or \"not stated\""},
    "severity":    {"type": "string",
                    "enum": ["low", "medium", "high", "critical", "not stated"]},
    "affected": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["location", "value", "unit", "source"],
        "properties": {
          "location": {"type": "string"},
          "value":    {"type": "string"},
          "unit":     {"type": "string",
                       "enum": ["households", "people", "families", "not stated"]},
          "source":   {"type": "string"}
        }
      }
    },
    "priority_needs": {"type": "array", "items": {"type": "string"}}
  }
}
```

### Pydantic: the contract in Python

Writing JSON Schema by hand is tedious and easy to get out of sync with your code. In Python the
standard tool (as of 2026) is **Pydantic**, a library where you declare the data shape as a
class. Pydantic then validates data against it, produces clear error messages, and generates the
JSON Schema for you:

```python
from typing import List, Literal

from pydantic import BaseModel, ConfigDict, Field, ValidationError


class Figure(BaseModel):
    model_config = ConfigDict(extra="forbid")            # additionalProperties: false
    location: str = Field(min_length=1)
    value: str = Field(description='As written in the report, e.g. "approx 1,200"')
    unit: Literal["households", "people", "families", "not stated"]
    source: str = Field(description="The words in the report the figure comes from")


class SitRep(BaseModel):
    model_config = ConfigDict(extra="forbid")
    district: str
    report_date: str = Field(pattern=r"^(\d{4}-\d{2}-\d{2}|not stated)$")
    hazard: str
    severity: Literal["low", "medium", "high", "critical", "not stated"]
    affected: List[Figure]
    priority_needs: List[str]
    response: List[str]
    gaps: List[str]


schema = SitRep.model_json_schema()          # -> the JSON Schema, for the prompt or the API

try:
    sitrep = SitRep.model_validate_json(reply_text)
except ValidationError as exc:
    for err in exc.errors():
        print(err["loc"], err["msg"])        # e.g. ('affected', 0, 'unit') Input should be ...
```

The lab validates with plain dataclasses and hand-written checks instead, so its tests need no
packages and you can see exactly what a validation library does. The lab README shows this
Pydantic version as a drop-in replacement.

### Designing schemas that models fill in well

A schema for an LLM is also a prompt: field names and descriptions are instructions. Guidelines:

- **Make "unknown" a first-class value.** If every field is required and "not stated" is not
  allowed, you have told the model to invent something. Choose one convention (the lab uses the
  string `"not stated"`, never `null`), put it in the rules, the example and the validator.
- **Keep source values as written.** `"value": "approx 1,200"` as a string preserves the
  hedge. Converting to the integer `1200` throws the "approx" away, and parsing the number is a
  job for code, later, deliberately.
- **Use enums for categories.** `unit` and `severity` have fixed allowed values, so the model
  cannot invent "persons" or "severe", and the validator catches it if it tries.
- **Ask for evidence.** A `source` field quoting the report makes every figure traceable and
  lets code check that the quote really appears in the report.
- **Name fields for meaning.** `priority_needs` beats `list2`. Add a `description` where the name
  is not enough.
- **Keep it shallow and small.** Deeply nested, 40-field schemas get filled less reliably. If
  the job is big, split it into two calls, as Class 1's decomposition would suggest.
- **Order fields deliberately.** Fields are generated in order. Put reasoning or evidence
  before conclusions if you use them.

### Three levels of enforcement

There are three ways to get JSON out of a model, each stronger than the last:

| Level | How | Guarantees | Gaps |
|---|---|---|---|
| **1. Ask in the prompt** | "Reply with JSON matching this schema. No prose." | Nothing. Usually works with modern models | Fences, prose, trailing commas, missing fields, extra fields |
| **2. JSON mode** | An API flag that forces syntactically valid JSON | It parses | Any shape: wrong fields, wrong types |
| **3. Schema-enforced structured outputs** | Pass the JSON Schema to the API; the provider constrains generation so output matches it | It parses *and* matches the schema's shape | Not the *content*: figures can still be invented; refusals and truncation still happen; schema features may be limited |

Provider support, **as of 2026** (these APIs change often, so check current documentation):

| Provider | Schema-enforced mode |
|---|---|
| **OpenAI** | Structured Outputs: `response_format` with a `json_schema` and `"strict": true` (Chat Completions), or the equivalent text-format setting in the Responses API. Strict mode requires every field to be listed as required and `additionalProperties: false`. |
| **Azure OpenAI** | The same Structured Outputs feature on supported model deployments and API versions. |
| **Anthropic** | Structured outputs that constrain Claude's reply to a JSON Schema on recent models. The long-standing alternative is to define a tool whose input schema is your schema and force the model to call it. |
| **LiteLLM** | Accepts `response_format` (including a Pydantic class) and translates it to each provider's mechanism where supported. |

With LiteLLM, a schema-enforced call looks like this:

```python
import json

import litellm
from sitrep_prompts import build_messages
from sitrep_schema import SITREP_JSON_SCHEMA, parse_sitrep

response = litellm.completion(
    model="openai/gpt-4o-mini",
    messages=build_messages(report),
    response_format={
        "type": "json_schema",
        "json_schema": {"name": "sitrep", "schema": SITREP_JSON_SCHEMA, "strict": True},
    },
    temperature=0,
)
sitrep = parse_sitrep(json.loads(response.choices[0].message.content))   # still validate
```

!!! tip "Use the strongest level available, and validate anyway"
    Schema-enforced output removes most retries, so use it when your provider supports it. But
    keep your own validation: providers differ in which schema features they enforce, you may
    switch provider or model, a refusal or a truncated reply can still come back, and **no mode
    checks that the figures are in the report.** The validator is your contract; the API mode is
    an optimisation.

## 6. Validation and the retry-with-feedback loop

Validation turns "the model replied" into one of two definite outcomes: **a valid object**, or
**a list of specific errors**. A good validator reports *every* problem with its location
(`affected[0].unit: 'persons' must be one of [...]`), not just the first. Those messages are
useful twice: in your logs, and as feedback to the model.

The lab's loop:

```python
def extract_sitrep(llm: LLM, report: str, max_attempts: int = 3) -> SitRep:
    messages = build_messages(report)
    replies, errors = [], []
    for _ in range(max_attempts):
        reply = llm(messages)
        replies.append(reply)
        try:
            return parse_sitrep(parse_json(reply))       # strip fences, parse, validate
        except ValidationError as exc:
            errors = exc.errors
            messages = messages + [{"role": "assistant", "content": reply},
                                   repair_message(errors)]
    raise ExtractionError(max_attempts, errors, replies)
```

Four design decisions in these lines:

1. **Tolerate the harmless, reject the rest.** `parse_json` strips a ```` ```json ```` fence
   (models add one even when told not to) but does *not* try to repair broken JSON by guessing.
   Guessing hides errors; the retry fixes them properly.
2. **Feed the error back, in context.** The retry keeps the conversation: the model sees its own
   reply as an `assistant` message, then a `user` message listing the exact errors. Models fix
   specific feedback ("severity: 'severe' must be one of [...]") far more reliably than a
   generic "try again". A blind retry is just another sample of the same distribution.
3. **Cap the attempts.** Three is typical. If three attempts fail, a fourth rarely helps. The
   input is usually the problem (an empty report, a different language, a document that is not
   a field report) and it needs a human. A retry loop is a loop, and every loop needs a budget
   (Class 6).
4. **Fail loudly, with evidence.** `ExtractionError` carries every raw reply and the last errors.
   The caller can put the report in a human review queue, and whoever reviews it can see what
   went wrong. It never returns a half-valid SitRep.

!!! warning "Two kinds of retry"
    Don't confuse this **repair retry** (the reply was invalid, so tell the model why) with a
    **transient retry** (the API timed out or was rate-limited, so wait and send the same
    request again). They need different code: transient retries use exponential backoff and
    never change the messages. Class 3 builds those.

### Beyond the schema

A schema checks shape. Many of the worst SitRep errors are well-formed: a correctly typed figure
that is not in the report. Add **semantic checks** in code after schema validation:

- every `source` quote appears in the report (ignoring case and whitespace);
- every `value` appears inside its `source`;
- `report_date` is not in the future;
- no figure appears in the output if the report contains no digits at all.

Feed failures from these checks into the same retry loop. This is Class 1's rule in practice:
the model proposes, code checks.

## 7. Prompts as code: templates, versions and tests

### Templates

A prompt that is assembled by string concatenation across three files cannot be reviewed.
Keep each prompt in **one place**, as a template with named slots:

```python
from string import Template

PROMPT_VERSION = "sitrep-extract/1.0.0"

USER_TEMPLATE = Template("""Extract the SitRep data from this report.

<report>
$report
</report>""")

def build_messages(report: str) -> list:
    return [{"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": USER_TEMPLATE.substitute(report=report.strip())}]
```

The lab uses the standard library's `string.Template`, whose `$name` placeholders don't clash
with the braces in JSON. Larger projects often use Jinja2 templates or keep prompts in separate
text files. The principle is the same: the prompt is a reviewable artefact, and `build_messages`
is the only function that assembles it.

### Versions

Give every prompt a **version** and log it with every call, together with the model name and
settings. When a SitRep in three weeks' time contains a strange figure, you need to answer
"which prompt, which model, which input?" in one query. Treat prompt changes like code changes:

- changed in a pull request, with a reviewer;
- a version bump for any change in behaviour (`1.0.0` → `1.1.0` for a new rule);
- a short changelog line: *"1.1.0: added rule 4, source quote for every figure, after
  invented Dorra figures in week 12"*;
- tests and evals run before release.

### Prompt tests

You cannot unit-test what a model will say, but there is a lot around the prompt you can test.
Three layers:

| Layer | Tests | Needs a model? | Example in the lab |
|---|---|---|---|
| **Prompt construction** | The rendered messages contain what they must: the rules, the schema, the delimiters, no data in the system prompt | No | `test_prompt_separates_instructions_from_data` |
| **Logic around the model** | Parsing, validation, retries and errors behave correctly for scripted replies | No: use `FakeLLM` | `test_malformed_then_fixed_retries_with_the_error` |
| **Model behaviour** | On a set of real inputs, the real model's outputs are valid and correct often enough | Yes | Class 7's evals; stretch challenge 3 starts one |

The first two layers run in milliseconds on every commit. The third is slower and costs money,
so it runs before releasing a new prompt version or model. Together they let you change a prompt
with confidence instead of hope.

## Key terms

- **System message / user message / assistant message:** stable developer instructions, the
  per-call input, and the model's replies (or examples written in its voice).
- **Delimiters:** markers such as `<report>…</report>` that separate data from instructions.
- **Prompt injection:** instructions hidden in data that try to override yours.
- **Few-shot example, example leakage:** a worked input → output pair in the prompt, and the
  model copying its content into real answers.
- **Chain of thought, reasoning field:** reasoning before answering, and a schema field placed
  first so reasoning is written before the answer.
- **Structured output:** a reply in a fixed, machine-readable shape, usually JSON.
- **JSON Schema:** a standard description of the shape JSON data must have.
- **Pydantic:** a Python library that declares data shapes as classes, validates data and
  generates JSON Schema.
- **JSON mode / structured-output mode:** API settings that guarantee valid JSON, or JSON that
  matches a given schema.
- **Validation, semantic check:** checking output against the schema, and checking its content
  against the source.
- **Repair retry vs transient retry:** re-asking with the validation errors, and resending the
  same request after a timeout or rate limit.
- **Prompt template, prompt version:** a prompt with named slots kept in one place, and the
  identifier logged with every call.
- **Prompt test:** an automated test of prompt construction or of the logic around the model.
