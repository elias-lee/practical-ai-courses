## 1. From the chat window to code: the messages API

When you use a chat tool, a lot happens that you never see. The tool keeps the conversation,
adds its own instructions, retries when the service is busy, stops you when you have used too
much, and shows the answer as it is written. When you call a model **from code**, all of that
becomes your job. That is what this class is about.

Think of the difference between eating in a restaurant and ordering wholesale from the kitchen's
supplier. In the restaurant, a waiter handles everything. With the supplier you place a precise
order in their format, you check the delivery, you chase late orders, and you pay per kilo. An
**API** (application programming interface) is that supplier's order form: a fixed format your
program uses to send a request and receive a reply.

Almost every model provider now uses the same basic shape, the **messages API**. You send a list
of **messages**, each with a **role** and some **content**:

```python
messages = [
    {"role": "system",    "content": "You summarize humanitarian field reports..."},
    {"role": "user",      "content": "Summarize these reports: <reports>...</reports>"},
]
```

- **system**: standing instructions for the whole conversation (Class 2's system prompt).
- **user**: what the person (or your program, acting for them) says.
- **assistant**: what the model said earlier. You include past assistant turns when you want a
  multi-turn conversation.

The reply contains more than text. The fields you will use most are:

| Field | What it tells you | Why you care |
|---|---|---|
| The **content** | The generated text | Your output, to be validated before use |
| The **stop reason** (`finish_reason`) | Why generation stopped: finished normally, hit the length limit, called a tool, or was filtered | A length stop means the answer is **truncated**; a filtered answer may be empty |
| **Usage** | Input (prompt) tokens and output (completion) tokens | This is what you pay for |
| **Model** | The exact model version that answered | Needed for reproducibility and cost |

One property surprises almost everyone: **the API is stateless**. The model remembers nothing
between calls. A "conversation" is an illusion created by your code sending the whole history
again with every request. That has three consequences you will meet all through this course:
long conversations cost more with every turn, the history is yours to store and protect, and
whatever you leave out, the model does not know.

## 2. LiteLLM: one interface for many providers

Each provider publishes its own **SDK** (software development kit: a library that wraps the API
for a particular language), and they differ in small, annoying ways: parameter names, error
classes, how usage is reported. If your SitRep code calls one provider's SDK directly, moving to
another provider, or running a cheaper model for one step, means rewriting it.

**LiteLLM** is an open-source Python library that puts one interface in front of more than a
hundred providers. You write the OpenAI-style call once, and the provider is chosen by a prefix
in the model string:

```python
import litellm

response = litellm.completion(
    model="azure/sitrep-gpt",               # or "openai/gpt-4o-mini", "anthropic/claude-sonnet-4-5"
    messages=messages,
    temperature=0,                           # as repeatable as the model allows
    max_tokens=600,                          # a ceiling on output length (and cost)
    timeout=60,                              # seconds; never wait forever
)
text   = response.choices[0].message.content
reason = response.choices[0].finish_reason   # "stop", "length", ...
usage  = response.usage                      # prompt_tokens, completion_tokens
print(litellm.completion_cost(completion_response=response))  # USD, from LiteLLM's price table
```

Model names are as of 2026; check your provider. The keys come from environment variables
(`AZURE_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`), never from your code (Section 10).

A provider's own SDK is also fine, and many organizations route all calls through an **AI
gateway** that centrally handles keys, logging, quotas and cost. Either way, **keep the provider
behind one small function of your own**. In the labs that function has this type:

```python
LLM = Callable[[List[Dict[str, str]]], str]   # messages in, text out
```

Anything with that shape can be plugged in: a LiteLLM call, a different provider, a scripted
fake for tests, a wrapper that adds retries, logging or cost tracking. That one line is what
makes the rest of this class testable.

## 3. Streaming

A 300-word SitRep takes a model several seconds to write. With a normal call, the user stares
at nothing until the whole answer arrives. With **streaming**, the provider sends the answer in
small pieces as they are generated, and your interface shows them straight away:

```python
stream = litellm.completion(model=model, messages=messages, stream=True, timeout=60)
parts = []
for chunk in stream:
    piece = chunk.choices[0].delta.content or ""
    print(piece, end="", flush=True)        # the user sees text appear immediately
    parts.append(piece)
full_text = "".join(parts)                  # validate THIS, after the stream ends
```

Streaming makes the app *feel* faster; it does not make it cheaper or the answer better. It
also changes three things you must handle:

- **Validation happens at the end.** You cannot check a JSON schema or a word limit until the
  last piece arrives, so don't act on partial output. Show it, then validate it.
- **Failures can happen half-way.** A stream can break after 200 words. Decide in your spec
  whether to retry from scratch, or keep the partial text and say so clearly.
- **Usage arrives last**, if at all. Some providers only report tokens in the final chunk, and
  only when you ask for it.

Use streaming where a human is watching; don't bother in an overnight batch job.

## 4. When calls fail: timeouts, rate limits and retries

A model API is a busy service on the other side of the internet. In any day of real use you
will see all of these:

| Failure | Typical signal | Retry? |
|---|---|---|
| **Rate limit**: too many requests or tokens per minute for your quota | HTTP 429 | Yes, after waiting |
| **Timeout**: no answer within your limit | Timeout exception, HTTP 408 | Yes |
| **Server error / overloaded** | HTTP 500, 502, 503, 504 (some providers use 529) | Yes |
| **Connection error** | Network exception | Yes |
| **Bad request**: malformed messages, context too long | HTTP 400 | **No**: fix the request |
| **Authentication / permission** | HTTP 401, 403 | **No**: fix the key or access |
| **Content filtered** | Provider-specific error or stop reason | **No**: retrying the same input gets the same result |

The first four are **transient**: the same request may well succeed a few seconds later. The
last three are **permanent**: retrying wastes time and money and hides a bug.

A **timeout** is the limit you set on how long to wait. Without one, a hung connection freezes
your app indefinitely. With one, a hang becomes an ordinary, retryable error. Choose it from
what you observe: if a normal SitRep call takes 8 seconds, 60 seconds is generous.

**Retries with exponential backoff.** When a call fails with a transient error, wait and try
again, doubling the wait each time: 1 s, 2 s, 4 s, 8 s… up to a cap. Doubling gives an
overloaded service room to recover. Add **jitter**, a small random extra delay, for a reason
anyone who has phoned a busy office understands: if everyone whose call dropped redials at
exactly the same second, the line is busy again for all of them. Jitter spreads the redials out.

Here is the lab's version. Every line maps to a requirement in the lab's spec:

```python
def call_with_retry(llm, messages, retries=3, backoff=1.0, max_backoff=30.0,
                    jitter=0.1, sleep=None, rand=random.random):
    sleep = sleep or time.sleep
    attempt = 0
    while True:
        try:
            return llm(messages)
        except Exception as exc:
            if not is_transient(exc):
                raise                                   # 400, 401, content filter: don't retry
            if attempt >= retries:
                raise RetryError(attempt + 1, exc) from exc   # give up loudly
            delay = min(max_backoff, backoff * (2 ** attempt))
            sleep(delay * (1 + jitter * rand()))        # 1 s, 2 s, 4 s ... plus up to 10%
            attempt += 1
```

Four details are worth copying into every project:

1. **`sleep` is injectable.** The tests pass a fake that records delays instead of waiting, so
   "retry three times with 1, 2 and 4 second waits" is tested in a millisecond. Any time you
   write code that depends on the clock, randomness or the network, make that dependency a
   parameter.
2. **Only transient errors are retried.** `is_transient()` in the lab's `llm.py` recognizes rate
   limits, timeouts, connection problems and 5xx errors by class name or status code, so the
   retry logic does not care which provider is behind it.
3. **Giving up is an explicit outcome.** `RetryError` says how many attempts were made and
   chains the last error (`from exc`), so the log shows *why*.
4. **Retries are a loop, so they need a budget.** Three retries is typical for interactive use.
   Beware of **stacked retries**: if your code retries 3 times, and the SDK underneath also
   retries 3 times, and a gateway retries 3 times, one failing request can become 64 attempts.
   Pick one layer to own retries (LiteLLM's `num_retries` and the official SDKs' `max_retries`
   are other valid choices) and switch the others off.

A retry is only safe when repeating the request does no harm. Asking for a summary twice is
harmless. Calling a tool that *sends an email* twice is not. Class 5 returns to this under the
name **idempotency**: an action is idempotent if doing it twice has the same effect as doing it
once.

## 5. Tracking tokens and cost

Providers charge per token, and **input and output tokens are priced differently**: output is
typically three to five times more expensive per token. The cost of one call is:

```text
cost = input_tokens  × price_per_input_token
     + output_tokens × price_per_output_token
```

Prices are usually quoted per million tokens. A worked example with illustrative prices of
USD 0.15 per million input tokens and USD 0.60 per million output tokens:

| Item | Tokens | Cost (USD) |
|---|---|---|
| One SitRep summary: 2,000 tokens in, 400 out | 2,400 | 0.0003 + 0.00024 = **0.00054** |
| 40 summaries a day for a year | ≈ 35 million | ≈ **7.90** |
| The same with a large model at 20× the price | | ≈ **158** |
| The same with a runaway loop that makes 50 calls per summary | | ≈ **395** at the small model's price |

The numbers are small until something multiplies them: a bigger model, a longer prompt, a
retry storm, or an agent loop without a budget (Class 6). That is why cost tracking is part of
the app, not an afterthought on the monthly invoice.

The lab's `CostTracker` accumulates calls, input tokens, output tokens and cost across a run,
and enforces an optional budget *before* each call:

```python
tracker = CostTracker(price_in_per_mtok=0.15, price_out_per_mtok=0.60, max_cost_usd=0.01)
llm = litellm_llm(model, on_usage=tracker.record)    # exact counts reported by the provider
summary = summarize(llm, reports, tracker=tracker)   # raises BudgetExceeded when spent
print(tracker.summary())   # calls=1 input_tokens=498 output_tokens=131 cost_usd=0.000153
```

Use the provider's reported usage whenever you can. When you can't (a fake in tests, or a
provider that doesn't report it), the lab estimates about four characters per token. That rule
of thumb holds for English. Text in Arabic, Chinese or Russian usually needs noticeably more
tokens for the same meaning, so a SitRep produced in six languages (say Arabic, Chinese, English,
French, Russian and Spanish) costs more than six times the English one. Measure it with your provider's token counter before you budget.

You will write the rest of this course's code with an AI assistant beside you. The tools have

Moving down the table, the tool does more work between your decisions. That is the point, and

## 7. Spec-first development: tests as the contract

The most reliable way to work with a coding agent is the same way you would brief a capable
contractor: write down what "done" means *before* the work starts. Think of the **terms of
reference** you would write for a consultant: the purpose, the deliverables, what is out of
scope, and how the work will be accepted. A **spec** (specification) is that document for
software, and **tests** are its acceptance criteria written as code.

The loop:

```text
 ┌─► 1. SPEC: one page. Purpose, interface, numbered requirements, non-goals.
 │   2. TESTS: one or more tests per requirement. Run them: they should FAIL.
 │   3. ONE SMALL STEP: ask the assistant to make one test (or one requirement) pass.
 │   4. RUN THE TESTS: all of them, every time.
 │   5. REVIEW THE DIFF: with the checklist in Section 8. Understand every line.
 │   6. COMMIT: a small, working, reviewed change.
 └── 7. NEXT REQUIREMENT (or update the spec first, if you learned something)
```

The lab's `SPEC.md` is a real example. An extract:

```text
R3 · Retries. Retry transient errors (rate limits, timeouts, connection and 5xx errors)
up to `retries` times (default 3) with exponential backoff: 1 s, 2 s, 4 s … capped at
30 s, plus up to 10% random jitter. Never retry other errors (bad request,
authentication, content filter): they propagate immediately.

R4 · Give up loudly. When retries are exhausted, raise `RetryError` naming the number of
attempts and chaining the last error. The CLI prints the error and exits with code 3.
```

and the test that turns R4 into a contract:

```python
def test_gives_up_after_n_retries():
    llm = FakeLLM([TransientError(f"503 #{i}") for i in range(4)])
    sleep = RecordingSleep()
    with pytest.raises(RetryError, match="4 attempts") as info:
        call_with_retry(llm, MESSAGES, retries=3, backoff=0.5, jitter=0, sleep=sleep)
    assert len(llm.calls) == 4                      # 1 attempt + 3 retries, then stop
    assert sleep.delays == [0.5, 1.0, 2.0]          # no sleep after the final failure
    assert isinstance(info.value.__cause__, TransientError)
```

Why this works so well with AI assistants:

- **Tests are an objective finish line.** "Make `pytest` pass" is a goal an agent can check
  by itself, over and over, without asking you. "Make it robust" is not.
- **Small steps keep the diff reviewable.** A 30-line change you can read properly beats a
  600-line change you skim. If a step goes wrong, you throw away minutes, not hours.
- **The spec survives the conversation.** Chat context is lost when the session ends; the spec
  and tests stay in the repository for the next person, and the next agent.
- **The spec is where the thinking is.** Deciding that a 401 must *not* be retried is an
  engineering judgement. Once it is written down, typing the code is the easy part.

**Guard the contract.** Agents under pressure to make tests pass will sometimes change the
*tests* instead of the code: loosening an assertion, adding a `skip`, or deleting the failing
case. Say explicitly in your instructions that tests may not be modified without your
approval, and check the diff of test files first when you review.

**Give the agent project context.** As of 2026, most coding agents read a project instructions
file automatically: `AGENTS.md` (a cross-tool convention), `CLAUDE.md`, or
`.github/copilot-instructions.md`, depending on the tool. Put the stable facts there: how to run
the tests, the coding style, "Python 3.9 compatible", "never add dependencies without asking",
"all data in this repo is fictional". It is a system prompt for your codebase.

## 8. Reviewing AI-written code

AI-written code is usually fluent, well formatted and plausibly commented, which makes it easy
to trust and easy to skim. Review it as you would review a pull request from a fast, confident
new colleague who has never seen your security policy. You are the author of record: if it
ships, it is your code.

| Check | Ask | Typical AI mistake |
|---|---|---|
| **Correctness** | Does it do what the spec says, including the numbers? Do *all* tests pass, run by you? | Off-by-one retries (3 attempts instead of 3 *retries*); the "happy path" works, the rest is guessed |
| **Tests** | Were tests changed? Do new tests assert something real? | Weakened or deleted assertions; tests that only check "no exception" |
| **Error handling** | Are errors specific, reported and surfaced? | `except Exception: pass`; retrying every error, including 401 |
| **Security** | Is any input trusted that shouldn't be? Any `eval`, shell calls, file paths from user input? | Building shell commands or SQL from strings; turning off TLS verification "to fix an error" |
| **Secrets** | Any key, token or password in code, logs, error messages or tests? | Printing the config "for debugging", including the key; a hard-coded key in an example |
| **Dependencies** | Is every new package necessary, real, maintained, licensed acceptably and pinned? | Adding a heavy library for one function; a **package name that doesn't exist** |
| **Edge cases** | Empty input, huge input, non-English text, missing fields, timeouts? | Nothing handles empty reports or a 2 MB file |
| **Cost and loops** | Can anything loop, retry or call the model without a limit? | A `while True` without a counter; retries stacked on SDK retries |

The dependency row deserves a warning of its own. Models sometimes **invent package names**
that sound right. Attackers have registered some of those invented names on public package
indexes with malicious code inside, a practice called *slopsquatting*. Before installing
anything an assistant suggests, check it exists, who maintains it and how widely it is used.

Here is a short function an assistant produced when asked to "add retries to the model call".
Read it before you read the notes below.

```python
def call_model(messages):
    for i in range(3):
        try:
            print(f"Calling {MODEL} with key {os.environ['OPENAI_API_KEY']}")
            return litellm.completion(model=MODEL, messages=messages).choices[0].message.content
        except Exception:
            time.sleep(1)
```

Review notes: (1) **Secret leak**: the key is printed to the console and any log. (2) **Retries every error**, including authentication failures and bad requests. (3) **No
backoff or jitter**: a fixed 1-second wait. (4) **No timeout**: one hung call blocks forever.
(5) **Silent failure**: after three failures it returns `None`, which the caller will happily
put into a SitRep. (6) It **sleeps after the final attempt** for no reason. (7) It is **not
testable** without a network and a real wait. Six lines, seven findings. None of them would
show up in a quick demo, which is the point.

A useful habit: ask a *second* model, in a fresh session, to review the diff against your
checklist (Prompt Lab Exercise 2). It adds to your review; it does not replace it.

## 9. "Vibe coding" vs spec-driven development

--8<-- "shared/sidebars/vibe-coding.md"

Vibe coding is not a sin. Describing what you want and letting an agent build it, checking
only that it seems to work, is a fast way to explore an idea. The question is where the result
ends up.

| Situation | Vibe coding acceptable? | Why |
|---|---|---|
| A throwaway prototype to show a manager what a SitRep dashboard *could* look like, on fictional data | **Yes** | Nothing depends on it; you will rebuild it properly if it is approved |
| A one-off script to rename 200 files in your own folder | **Yes, with a backup** | Low stakes, easy to check the result by looking |
| Exploring an unfamiliar library to learn its API | **Yes** | The goal is learning, not the code |
| A tool colleagues will use every day | **No** | Other people will depend on behaviour nobody specified or reviewed |
| Anything that handles personal data, credentials or data above "public" | **No** | Security and privacy failures are invisible in a demo |
| Anything whose output becomes an official figure, e.g. a SitRep sent to partners | **No** | Errors propagate into decisions about people's lives and resources |
| Code that calls paid APIs in loops, or runs unattended | **No** | Runaway cost and silent failure |

A practical middle path: **vibe code the prototype, then throw it away.** Once you know what you
want, write the spec, write the tests, and rebuild in small reviewed steps. The prototype was
the cheapest possible requirements workshop.

## 10. Project hygiene

Three habits prevent most of the embarrassing incidents in AI projects.

**Secrets live in environment variables, never in code.** An **environment variable** is a
named value set in your shell or your deployment platform, which your program reads at run time:

```python
import os
api_key = os.environ["OPENAI_API_KEY"]    # fails loudly if missing, which is what you want
```

For local development, a `.env` file (loaded by a tool such as `python-dotenv`) is convenient.
It must be listed in `.gitignore` so it is never committed. In production, keys come from a
**secrets manager** (such as Azure Key Vault or a cloud equivalent), not from files. If a key is
ever committed, pushed or pasted into a chat, **rotate it immediately** (revoke it and issue a
new one). Deleting the commit is not enough: git history, forks and caches keep copies.

**`.gitignore` is part of the project.** The lab's contains:

```text
.env
*.key
.venv/
__pycache__/
.pytest_cache/
```

Add secret scanning as well: many code hosts scan pushes for key patterns, and tools such as
`gitleaks` or `detect-secrets` can run as a pre-commit check on your machine.

**Pin your dependencies.** "Works on my machine" usually means "my machine has a different
version of a library". **Pinning** records the exact version of every package you depend on,
so that everyone, including CI (continuous integration: the service that runs your tests on
every change) and the production server, installs the same thing:

```bash
pip install litellm pytest
pip freeze > requirements.lock        # exact versions, e.g. litellm==<version>
pip install -r requirements.lock      # on any other machine
```

Tools such as `uv` or `poetry` do the same with a lock file. AI libraries release very often;
upgrade on purpose, run the tests, and commit the new lock file.

## Key terms

- **API / messages API**: the fixed request format for calling a model: a list of messages,
  each with a role (system, user, assistant) and content.
- **SDK**: a library that wraps an API for a particular programming language.
- **LiteLLM**: an open-source library giving one interface to many model providers.
- **Stateless**: the model remembers nothing between calls; your code resends the history.
- **Stop reason (`finish_reason`)**: why generation ended, e.g. finished, length limit, filtered.
- **Streaming**: receiving the answer in pieces as it is generated.
- **Timeout**: the longest your code will wait for a reply before treating the call as failed.
- **Rate limit**: a provider's cap on requests or tokens per minute; exceeding it returns 429.
- **Transient vs permanent error**: worth retrying later vs will fail the same way again.
- **Exponential backoff, jitter**: doubling the wait between retries, plus a little randomness.
- **Idempotent**: safe to repeat; doing it twice has the same effect as doing it once.
- **Token usage, cost tracking, budget**: counting input and output tokens, pricing them, and
  refusing further calls past a limit.
- **Coding assistant, coding agent**: an AI that suggests code vs one that plans, edits files
  and runs commands to complete a task.
- **Spec, spec-first development**: a written definition of done, written before the code.
- **Tests as the contract**: tests that encode the spec and define when a change is finished.
- **Vibe coding**: accepting AI-generated code by whether it seems to work, without close review.
- **Slopsquatting**: publishing malicious packages under names that AI tools tend to invent.
- **Environment variable, secrets manager**: where keys live instead of code.
- **Pinned dependencies, lock file**: recording exact package versions so every install is
  the same.
